# Project Setup

Your project has been accepted into Civic Tech DC—congratulations! Now it’s time to turn the idea into a project that volunteers can actually join and contribute to.
Project Setup is split into two parts: getting ready and project night. You need to complete everything in getting ready before participating in your first project night.

- A clear problem and community need
- A named project partner or community connection
- A project lead
- A defined first milestone
- A realistic project roadmap
- Clear roles and expectations
- A GitHub repository
- A Slack channel
- Basic project documentation
- Initial tasks for contributors
- A plan for communicating progress

---

## 1. Define Your Project

Before setting up tools, make sure you determine what the project is actually trying to accomplish. Please make a copy of the **Project Brief** template and share it in your project’s Slack channel and with new contributors.

## 2. Set Expectations

Civic Tech DC projects are volunteer-run. Setting expectations early helps prevent projects from becoming dependent on a small number of people.

### Commit yourself as the Project Lead

As the project lead, you are responsible for keeping the project moving. Here are some of the responsibilities you will be expected to support:

- Keep the project scope clear
- Coordinate with the partner
- Help contributors find work
- Communicate priorities
- Keep documentation up to date
- Raise blockers when the project needs help
- Help prepare for transition or handoff

### Volunteer Contributors

Volunteers contribute based on their availability and interests. Contributors may work on a variety of tasks, such as coding, design, data wrangling, project management, documentation, research, outreach, or community engagement.
Please make a copy of the **Volunteer Contributor Needs** template, fill it out with the specific roles and tasks your project needs, and share it in your project’s Slack channel and with new contributors. [Volunteer Contributor Needs - Google Docs](https://docs.google.com/document/d/1f1ET0w1poddBuuiNOyAjc6FS_tc4Xlr6fr2A5-xO5Og/edit?tab=t.0)
If you are not sure what types of contributions your project needs, check out the **Participation Pathways** page to explore the different ways volunteers can contribute.

## 3. Set Goals and Milestones

A project needs more than a general goal. Break the work into milestones that give the team a clear sense of progress.

### Start With One Milestone

Your first milestone should be achievable and meaningful.
For example:

> **Goal:** Make it easier for residents to find local cooling centers.

> **First milestone:** Build and test a basic searchable map containing the current cooling center dataset.

The first milestone does not need to be the final product.

### Build a Roadmap

For each milestone, identify:

| **Milestone** | **What will be completed?** | **How will we know it is done?** |
| ------------- | --------------------------- | -------------------------------- |
| 1. Discovery  | Interview potential users   | 3 user interviews completed      |
| 2. Prototype  | Build initial prototype     | Partner can test prototype       |
| 3. Pilot      | Test with users             | Feedback collected from pilot    |
| 4. Launch     | Deploy first version        | Partner can use the tool         |

Keep the roadmap flexible. Volunteer projects often change as you learn more.
**Resource:** [Project Roadmap Template]

### Review Your Scope

Before recruiting a large team, ask:

- Can this realistically be accomplished by volunteers?
- What is essential for the first milestone?
- What can wait?
- What dependencies could block the project?
- What happens if fewer volunteers join than expected?

If the project is too large, reduce the scope rather than assuming more volunteers will solve the problem.

## 4. Set Up Your Tools

Once the project has a clear direction, set up the basic infrastructure contributors will use.

### GitHub

Every technical project should have a repository in the Civic Tech DC GitHub organization.
The repository should include:

- `README.md`
- `CONTRIBUTING.md`
- License
- Project documentation
- Issue labels
- Initial issues or tasks

**Resources:**

- [GitHub Organization Access](https://chatgpt.com/resources/github/)
- [README Template]
- [CONTRIBUTING.md Template]

### Slack

Create the project's Slack channel using the standard naming convention:

```text
#proj-[name]-[year]
```

### Slack

Create the project's Slack channel using the standard naming convention:
proj-[name]-[year]
The channel should include a pinned **Start Here** message with:

- Project description
- Project lead
- Partner contact
- Links to GitHub and documentation
- Meeting schedule
- How new contributors can get started

**Resource:** [Slack Project Setup Guide]

### Shared Folder 

Create a central location for project documentation. At minimum, it should include:

- What the project does
- Who it serves
- How to contribute
- How to run the project
- Current priorities
- Important decisions
- Partner and stakeholder information

Once your project has completed Project Setup, you are ready to bring the project to a Project Night!

## Hosting Your First Project Night

Your first Project Night is an opportunity to introduce your project to the Civic Tech DC community and start finding contributors.
You do not need to have everything figured out before bringing your project to Project Night. The goal is to clearly explain what you are working on, what problem you are trying to solve, and where you need help.
Before your first Project Night, make sure you can briefly explain:

- **The problem:** What problem are you trying to solve?
- **The people:** Who experiences this problem?
- **The partner:** Who are you working with?
- **The goal:** What are you trying to accomplish?
- **The current stage:** What has been done so far?
- **The next step:** What do you need help with right now?
- **The roles:** What can contributors work on?

Your project should also have a clear place for people to get started, such as a GitHub repository, project documentation, research task, design file, or other project resource.
At Project Night, keep your introduction short and focus on what people can actually do. You do not need to give a long presentation about the entire project.
A good project introduction might sound like:

> “We’re working with [partner] to address [problem]. We’re currently at [stage]. Tonight, we’re looking for people who can help with [specific tasks]. You don’t need to have [specific skill] to participate, and we have a few ways to get started.”

After introducing the project, spend the rest of the evening working with contributors. Help new people understand the project, answer questions, and identify a small first contribution they can make.

## Build Your First Contributor Tasks

Now that you have started building a team, you can begin defining the work that needs to happen next. Some tasks are difficult to identify before you have contributors because you may not yet know what skills, interests, or capacity are available.

### Create Initial Issues

Start with a small number of clearly defined tasks.
Good first issues should:

- Have a clear description
- Explain what needs to be done
- Identify relevant files or resources
- Include `good-first-issue` when appropriate
- Explain what a completed task looks like

Remember that **everything counts**. Create opportunities for technical and non-technical contributors.
Examples include:

- Research existing solutions
- Interview users
- Clean data
- Create wireframes
- Write documentation
- Test an existing feature
- Improve accessibility
- Build a frontend component
- Analyze data
- Identify potential community partners
- Write or review project content

You do not need to create dozens of issues at once. Start with a few meaningful tasks that contributors can actually complete.

## Establish Your Communication Rhythm

Projects should have a predictable way for people to stay informed.
At minimum, establish:

- Project Night check-ins
- A regular project team meeting when needed
- Weekly or biweekly project updates
- A place for contributors to ask questions
- A process for escalating blockers

The exact cadence can vary by project. The goal is not to create more meetings; it is to make sure contributors know what is happening and where to go when they need help.
